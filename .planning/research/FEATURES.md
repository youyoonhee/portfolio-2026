# Feature Research

**Domain:** 국내 이직용 웹 퍼블리셔(앱·반응형 웹) 포트폴리오 — 정적 웹사이트 + 같은 디자인의 제출용 PDF
**Researched:** 2026-11-11
**Confidence:** MEDIUM — 채용공고 요건(웹표준·웹접근성·크로스브라우징·반응형)은 여러 공고에서 반복 확인했다(MEDIUM~HIGH). 반면 "면접관이 실제로 무엇을 보는지"에 대한 1차 자료(설문, 인터뷰)는 찾지 못했고, 교육 업체·블로그 글과 실무 관행에서 추론한 부분이 많다(LOW~MEDIUM). 추론한 부분은 본문에 표시했다.

---

## 핵심 관찰 (요구사항 정의자를 위한 요약)

1. **사이트 자체가 1번 작업물이다.** 국내 퍼블리셔 공고의 자격요건은 거의 그대로 "웹표준 / 웹접근성 / 크로스브라우징 / 반응형"이다(원티드·리멤버 공고 다수). 검토자는 지원자가 "할 줄 안다"고 쓴 내용을 포트폴리오 사이트에서 바로 확인한다. 개발자도구를 열어 마크업을 보고, 창 크기를 줄여 보고, Tab 키를 눌러 본다(실무 관행에서 추론, MEDIUM). 그러니 사이트에 화려한 효과가 많은 것보다 **마크업이 깨끗하고 반응형이 깨지지 않는 것**이 더 큰 점수가 된다.
2. **검토 시간이 짧다.** 채용 담당자는 첫 화면과 프로젝트 목록만 훑어보는 경우가 많다. 그래서 "회사 · 기간 · 플랫폼 · 담당 · 기여도"가 **카드 한 장에서 바로** 읽혀야 한다. PROJECT.md의 Core Value와 같은 이야기다.
3. **에이전시·SI 출신 퍼블리셔는 "링크가 없는 작업"이 흔하다.** 운영 종료, NDA, 고객사 내부 시스템, 기사만 남은 작업 같은 경우다. 링크 상태를 정직하고 일관되게 표시하는 것 자체가 신뢰를 준다. 링크가 깨져 있는 게 링크가 없는 것보다 더 나쁘다(검토자는 깨진 링크를 "관리 안 됨"으로 읽는다).
4. **기여도 %는 국내 퍼블리셔 포트폴리오에서 사실상 표준 항목이다.** 다만 숫자만으로는 약하다. "무엇을 맡았는지"를 한 줄로 붙여야 숫자가 해석된다(예: "50% — 2인 1팀, 기획전 템플릿 마크업과 유지보수 담당").
5. **PDF는 여전히 필수다.** 국내 채용 플랫폼(사람인·잡코리아·원티드·리멤버)과 헤드헌터는 첨부 파일 제출이 기본이다. 웹 링크는 PDF 안에 함께 넣는 보조 경로로 쓰는 경우가 많다.

## Feature Landscape

### Table Stakes (없으면 감점되는 것)

검토자가 당연히 있을 거라 기대하는 것들이다. 있어도 가산점은 없지만, 없으면 바로 감점된다.

#### A. 콘텐츠 섹션

| Feature | Why Expected | Complexity | Notes |
|---------|--------------|------------|-------|
| **Hero / 한 줄 소개** | 처음 3초 안에 "누구이고 어떤 직무인지"가 보여야 한다 | LOW | 원본 카피 "화면 너머의 경험까지 섬세하게. 앱, 반응형 웹 퍼블리셔 유윤희 입니다."를 그대로 쓴다. 직무명(앱·반응형 웹 퍼블리셔)과 총 경력 기간이 첫 화면에 보이게 한다. 경력 기간은 경력 데이터에서 계산한 값만 쓰고 지어내지 않는다 |
| **Skills 섹션** | 공고 자격요건과 바로 맞춰 보는 항목이다 | LOW | 숙련도를 **"주력 / 경험"** 두 단계 텍스트로 나눈다(원본 PDF 구분과 같다: HTML5·CSS3·SCSS·JS(ES6+) 주력, TypeScript·Angular·Vue 경험). 퍼센트 막대 그래프는 쓰지 않는다(Anti-Features 참고) |
| **Career 타임라인** | 회사 4곳의 재직 기간과 이직 흐름을 한눈에 보여 준다 | LOW | 최신순으로 회사명, 기간(YYYY.MM ~ YYYY.MM), 한 줄 업무 요약, 해당 프로젝트로 가는 앵커 링크를 둔다. 시맨틱하게는 `<ol>` + `<time datetime>`으로 짠다 |
| **프로젝트 목록 (13개 전부)** | 원본 PDF 내용을 빠짐없이 옮기는 게 요구사항이다 | MEDIUM | 회사별로 묶고 최신순으로 놓는다. 모든 프로젝트를 같은 스키마로 쓴다(아래 C 참고) |
| **Contact (이메일만)** | 연락할 수단이 없으면 포트폴리오가 쓸모없다 | LOW | `mailto:` 링크와 이메일 텍스트를 함께 보여 준다(복사할 수 있게). 웹에는 전화번호를 넣지 않는다. GitHub 링크는 있으면 같이 둔다 |
| **PDF 다운로드 버튼** | 담당자가 사내 공유나 결재용으로 파일이 필요하다 | LOW (버튼) / HIGH (PDF 생성은 별도) | 헤더나 Contact에 "PDF 다운로드"를 둔다. **웹에 올리는 PDF는 전화번호를 뺀 버전**이어야 한다. 전화번호가 들어간 제출용 PDF는 저장소나 사이트에 올리지 않는다(개인정보 제약) |

#### B. 퍼블리싱 품질 (사이트 자체가 증거)

| Feature | Why Expected | Complexity | Notes |
|---------|--------------|------------|-------|
| **반응형 375 / 768 / 1440, 가로 스크롤 없음** | "반응형 웹 퍼블리셔"인데 사이트가 모바일에서 깨지면 바로 탈락감이다 | MEDIUM | 모바일 우선 CSS로 짠다. 표, 긴 URL, 이미지에서 overflow가 나지 않는지 확인한다. 320px에서도 깨지지 않으면 더 좋다 |
| **시맨틱 마크업** | 공고 1순위 요건이 웹표준이고, 검토자가 개발자도구로 직접 본다 | LOW | `header/nav/main/section/article/footer`, 제목 계층(h1은 하나, 건너뛰지 않기), 프로젝트 카드는 `<article>`, 메타 정보는 `<dl>`로 짠다. W3C Validator 오류 0개를 목표로 한다 |
| **키보드 접근성** | 웹접근성은 공고에서 반복되는 요건이다 | LOW~MEDIUM | 본문 바로가기(skip link), `:focus-visible` 스타일, 논리적인 Tab 순서. 모달/라이트박스를 쓴다면 포커스 트랩, ESC로 닫기, 닫은 뒤 포커스 복귀까지 해야 한다 |
| **대체 텍스트** | 스크린샷이 중심인 사이트라 빠지면 접근성이 무너진다 | LOW (단, 스크린샷마다 작성해야 함) | 장식이 아닌 스크린샷은 "무엇이 보이는 화면인지" 쓴다(예: "원데이보험 앱 메인 인트로 화면"). 장식 이미지는 `alt=""` |
| **충분한 명도 대비 (WCAG AA 4.5:1)** | 포인트 컬러를 쓸 때 가장 자주 틀리는 부분이다 | LOW | 포인트 컬러를 정할 때 본문 텍스트와 링크 대비를 같이 확인한다. 회색 보조 텍스트가 3:1 아래로 내려가지 않게 한다 |
| **크로스브라우징 (Chrome, Edge, Safari/iOS)** | 공고 고정 요건이다 | MEDIUM | iOS Safari에서 `100vh`, 탭 하이라이트, `position: sticky`, 폰트 렌더링, 이미지 `aspect-ratio`를 확인한다. 실기기나 BrowserStack에서 테스트한다 |
| **이미지 최적화와 빠른 로딩** | 스크린샷 13개 이상이라 그대로 넣으면 무겁다. 첫인상이 "느림"이 되면 안 된다 | MEDIUM | WebP/AVIF와 `<picture>`, `width/height` 명시(CLS 방지), `loading="lazy"`(첫 화면 제외), `srcset`. 빌드 도구가 없으니 이미지는 미리 변환해서 커밋한다 |
| **메타 정보 / OG 태그** | 카톡이나 메일로 링크를 공유할 때 미리보기가 깨지면 완성도가 떨어져 보인다 | LOW | `title`, `description`, `og:title/description/image`, favicon, `lang="ko"` |
| **깨진 링크 0개** | 깨진 링크는 "관리 안 됨" 신호다 | LOW (점검 습관) | 배포 직전에 모든 외부 링크를 로그아웃 상태, 다른 기기에서 열어 본다. 운영 종료된 서비스 링크는 걸지 않는다(아래 C의 상태 배지로 처리) |

#### C. 프로젝트 표현 스키마 (가장 중요)

모든 프로젝트를 **같은 필드 순서**로 보여 준다. 그래야 검토자가 13개를 빠르게 훑을 수 있다.

| 필드 | 필수 | 표현 방식 | Notes |
|------|------|-----------|-------|
| 프로젝트명 | 필수 | 제목(h3) | 서비스명 + 고객사(예: "피치(Peach) — 교보생명 금융 마이데이터 앱") |
| 회사(소속) | 필수 | 메타 | 에이전시/SI 소속과 고객사를 구분해서 쓴다(소속: 비스톤스 / 고객사: CJ) |
| 기간 | 필수 | `<time>` | 원본 PDF에 프로젝트 단위 기간이 없으면 회사 재직 기간을 쓰고, 기간을 지어내지 않는다 |
| 플랫폼 | 필수 | 태그 `App` / `Web` / `반응형 Web` / `Hybrid` | 앱·반응형 웹 퍼블리셔라는 정체성을 보여 주는 핵심 필드다 |
| 작업 유형 | 권장 | 태그 `구축` / `유지보수` / `리뉴얼` / `운영` | 국내 검토자는 신규 구축 경험과 유지보수 경험을 구분해서 본다(추론, MEDIUM) |
| 담당 업무 | 필수 | 불릿 2~4개 | 화면 단위로 쓴다("메인 인트로, 상품소개 리뉴얼", "보험료 산출기 화면 유지보수") |
| 퍼블 기여도 | 필수 | 숫자 + 맥락 한 줄 | "100%" 단독보다 "100% — 단독 퍼블리싱"이 낫다. 원본에 있는 맥락(2인 1팀 등)만 쓴다 |
| 사용 기술 | 권장 | 태그 | HTML/SCSS/jQuery/Angular 등. 원본에 명시된 것만 쓴다 |
| 스크린샷 | 필수 | 대표 1장 + 상세 n장 | 앱은 세로 모바일 프레임, 웹은 데스크톱+모바일 쌍으로 보여 주면 반응형 작업임이 바로 드러난다 |
| 링크 / 운영 상태 | 필수 | 상태 배지 + 링크 | 아래 상태 체계 참고 |

**링크 / 운영 상태 체계 (일관된 배지):**

| 상태 | 배지 텍스트 | 링크 처리 | 해당 프로젝트(원본 기준) |
|------|-------------|-----------|--------------------------|
| 운영 중 | `운영 중` | 서비스 URL (새 창, `rel="noopener"`, 새 창임을 알리는 텍스트/aria) | 하나손해보험, 삼성 E스토어 등 (링크가 살아 있는지 확인 필요) |
| 운영 종료 | `운영 종료` | 링크 없음. 스크린샷이 유일한 증거라 스크린샷 비중을 키운다 | 피치, 로드필 |
| 외부 자료만 | `소개서 링크` / `관련 기사` | 소개서·기사 URL. 라벨에 "서비스가 아니라 기사"임을 밝힌다 | ADDY(소개서), EXAONE universe(기사) |
| 앱 설치 파일만 | `APK 보유` | 공개 링크 없음. "요청 시 시연 가능"이라고 쓴다 | puring |
| 비공개 / 내부 시스템 | `비공개 (NDA)` | 링크 없음. 스크린샷 공개 범위도 확인한다 | 관리자 연동 페이지 등 해당 시 |

- 핵심 원칙: **"링크 없음"을 숨기지 말고 이유를 라벨로 밝힌다.** 검토자가 링크를 눌러 404를 보는 일이 없어야 한다.
- 스크린샷을 공개해도 되는지(NDA, 고객사 정책)는 사용자가 확인해야 할 사항이다. 필요하면 개인정보나 내부 데이터 부분을 블러 처리한다.

### Differentiators (경쟁 우위)

대부분의 퍼블리셔 포트폴리오는 "PDF를 웹으로 옮긴 것"에서 멈춘다. 아래는 같은 비용으로 "이 사람은 퍼블리싱을 제대로 한다"를 증명하는 항목들이다. 모두 Core Value(사이트 자체가 실력의 증거)에 맞춘 것이다.

| Feature | Value Proposition | Complexity | Notes |
|---------|-------------------|------------|-------|
| **"이 사이트는 이렇게 만들었습니다" 섹션 (Colophon / Build Notes)** | 품질을 주장하는 데서 끝나지 않고 검증할 수 있게 해 준다. 검토자가 개발자도구를 열기 전에 답을 준다 | LOW | 푸터 근처에 짧게 둔다. "순수 HTML/CSS/JS, 프레임워크·빌드 도구 없음 / 시맨틱 마크업 / 키보드 탐색 지원 / WCAG 2.2 AA 대비 / Chrome·Edge·Safari(iOS) 테스트 / 375·768·1440 반응형". 각 항목은 **실제로 지킨 것만** 쓴다 |
| **GitHub 소스 링크** | 공고 1순위인 웹표준을 코드로 바로 보여 준다. 에이전시 작업은 소스를 공개할 수 없으니 이 사이트 코드가 유일하게 공개할 수 있는 코드 샘플이다 | LOW | 공개 저장소로 만든다. README에 폴더 구조, CSS 설계(변수, BEM 같은 네이밍 규칙), 접근성 체크리스트를 쓴다. 전화번호가 든 파일(`.planning/source/`, 제출용 PDF)은 반드시 gitignore한다 |
| **Lighthouse / 검증 결과 표기** | 숫자는 빠르게 읽히는 증거다 | LOW (측정) / 유지는 MEDIUM | Colophon에 "Lighthouse Performance/Accessibility/Best Practices/SEO 점수(측정일)" 또는 W3C Validator 통과를 적는다. **실제 측정값만, 측정일과 함께** 쓴다. 점수 배지를 자동 갱신하는 장치는 만들지 않는다(정적이면 충분). 100점이 안 나온 항목을 100점으로 쓰면 역효과다 |
| **프로젝트별 "퍼블리싱 포인트" 한두 줄** | 결과 화면만 보여 주는 것과 무엇을 고민했는지 보여 주는 것은 차이가 크다(교육 업체 자료에서 공통으로 강조, MEDIUM) | LOW (작성) | 예: "관리자에서 등록하는 이벤트 페이지를 템플릿화", "Angular 컴포넌트 구조 안에서 반응형 처리". **원본 PDF에 근거가 있는 내용만** 쓴다. 근거가 없으면 비워 두고 사용자에게 확인을 요청한다(콘텐츠 정확성 제약) |
| **기여도 시각화 (텍스트 우선)** | 13개 프로젝트의 기여도 분포(30%에서 100%로 성장)가 경력 흐름을 보여 준다 | LOW | 숫자 텍스트를 주로 쓰고, 보조로 얇은 바를 둘 수 있다. 바에는 `aria-hidden`을 걸고 숫자 텍스트를 실제 정보로 둔다 |
| **플랫폼 / 회사 필터** | App 작업과 Web 작업만 골라 보고 싶은 검토자(앱 직무 지원 등)에게 편하다 | MEDIUM | 순수 JS로 필터 버튼을 만든다(`aria-pressed`, 결과 개수를 `aria-live`로 알림). JS가 꺼져 있어도 전체 목록이 보이게(점진적 향상) 한다. **13개라 없어도 된다.** v1.x 후보 |
| **반응형을 시연하는 스크린샷 구성** | 같은 화면을 데스크톱과 모바일 쌍으로 보여 주면 "반응형 퍼블리셔"임이 한 장으로 증명된다 | LOW (레이아웃) / 사용자 이미지에 의존 | 사용자가 모바일과 데스크톱 캡처를 둘 다 가진 프로젝트에만 쓴다 |
| **웹 = PDF 같은 소스 (print stylesheet)** | 한 소스에서 웹과 PDF가 같은 디자인으로 나오는 것 자체가 퍼블리싱 역량이다(`@media print`, `@page`, 페이지 나눔 제어) | HIGH | 전화번호 같은 PDF 전용 콘텐츠는 별도 처리가 필요하다(STACK/ARCHITECTURE 연구와 연동). Colophon에 "이 PDF는 같은 HTML의 인쇄 스타일로 만들었습니다"라고 적으면 차별점이 된다 |
| **다크모드 / `prefers-reduced-motion` 대응** | 세심함을 보여 주는 신호다 | LOW~MEDIUM | `prefers-reduced-motion`은 모션을 쓴다면 필수에 가깝다(LOW). 다크모드는 대비 검증 비용이 두 배라 v1.x로 미룬다 |

### Anti-Features (일부러 만들지 않을 것)

| Feature | Why Requested | Why Problematic | Alternative |
|---------|---------------|-----------------|-------------|
| **스킬 퍼센트 막대 / 원형 게이지 ("HTML 95%")** | 흔하고 시각적으로 꽉 차 보인다 | 기준이 없는 자기 평가라 실무 면접관이 가장 불신하는 요소다. "95%면 나머지 5%는 뭔가요?" 같은 질문을 부른다. 차트에 접근성 처리도 따로 해야 한다 | "주력 / 경험" 텍스트 두 단계 + 해당 기술을 쓴 프로젝트 연결 |
| **과한 스크롤 애니메이션, 패럴랙스, 커스텀 커서, 풀페이지 스크롤 강제** | "퍼블리셔니까 인터랙션을 보여 줘야지"라는 생각 | 검토 시간이 짧은데 내용이 늦게 나타난다. 모바일 성능, 접근성(전정 장애), 키보드 탐색이 망가진다. 미니멀 방향과도 충돌한다 | 짧은 fade 정도만 쓰고 `prefers-reduced-motion`을 존중한다. 인터랙션 역량은 프로젝트 설명으로 보여 준다 |
| **인트로 로딩 화면 / 스플래시** | 브랜딩 | 첫 화면이 늦게 뜨는 것 자체가 감점이다. LCP도 나빠진다 | Hero 텍스트를 바로 렌더링한다 |
| **문의 폼** | 연락 편의 | 정적 호스팅이라 백엔드나 외부 서비스가 필요하고 스팸이 들어온다. 이미 Out of Scope다 | `mailto:` + 이메일 텍스트 |
| **웹에 전화번호 / 상세 개인정보 (주소, 생년월일, 사진 필수 아님)** | 이력서 관행 | 공개 사이트는 크롤링된다. 개인정보 제약이 있다 | 전화번호는 제출용 PDF에만 넣고, 그 PDF는 공개 경로에 두지 않는다 |
| **운영 종료 서비스에 원래 URL 걸기** | "링크가 있어야 진짜 같아서" | 404나 도메인 만료 페이지(스팸 사이트로 넘어가기도 한다)로 이어진다 | `운영 종료` 배지 + 스크린샷 |
| **Wayback Machine 링크를 기본 링크로 쓰기** | 운영 종료 서비스를 증명하려고 | 아카이브가 깨져 있거나 로그인 화면만 남은 경우가 많고, 앱(피치)은 아카이브되지 않는다. 확인 비용에 비해 효과가 작다 | 기본은 스크린샷으로 한다. 사용자가 확인한 정상 아카이브가 있을 때만 보조 링크로 둔다 |
| **원본에 없는 성과 수치 ("전환율 30% 향상")** | 일반 포트폴리오 가이드가 "수치로 성과를 쓰라"고 권한다 | 콘텐츠 정확성 제약을 위반한다. 면접에서 근거를 물으면 무너진다 | 화면 단위의 담당 범위와 기여도처럼 사실인 정량 정보를 쓴다 |
| **프레임워크 / SPA 라우팅 / 빌드 파이프라인** | 모던해 보인다 | Out of Scope다. 순수 마크업 역량을 보여 준다는 목적과 반대된다. SPA는 SEO, 공유 미리보기, PDF 출력을 복잡하게 만든다 | 단일 `index.html`(필요하면 앵커 섹션)로 만든다 |
| **프로젝트마다 별도 상세 페이지** | 사례 연구식 구성 | 13개 페이지를 따로 관리해야 하고, 검토자의 클릭 수가 늘어나고, PDF 구성과 어긋난다. 콘텐츠도 프로젝트당 몇 줄 수준이라 페이지를 채울 만큼 많지 않다 | 한 페이지 안의 카드로 보여 주고, 스크린샷은 라이트박스(또는 카드 안 갤러리)로 키운다 |
| **블로그, 방문자 카운터, 방명록, 배경음악, 챗봇** | 콘텐츠를 늘리려고 | 범위 밖이고 유지 비용이 든다. 미니멀 방향과도 맞지 않는다 | 없음 |
| **무거운 외부 라이브러리 (jQuery 플러그인 슬라이더, GSAP 전체, 아이콘 폰트 전체)** | 빠르게 구현하려고 | 성능 점수가 떨어진다. "직접 만든 코드"라는 메시지가 약해진다 | 네이티브 `<dialog>`, CSS scroll-snap, 인라인 SVG |
| **Lighthouse 점수 자동 배지 / CI 연동** | 자동화가 멋져 보인다 | 정적 포트폴리오에 비해 과한 설정이다. 측정 환경에 따라 점수가 흔들려 낮게 표시될 위험도 있다 | 측정값과 측정일을 텍스트로 한 번 적는다 |
| **웹접근성 인증마크 표기** | 신뢰 표시 | 실제 인증을 받지 않았다면 허위 표기다. 공고에서도 인증마크를 요구하는 경우는 확인되지 않았다(KWCAG는 공공 공고에서만 언급됨) | "KWCAG 2.2 / WCAG 2.2 AA를 기준으로 자체 점검"이라고 사실대로 쓴다 |

## Feature Dependencies

```
[프로젝트 데이터 스키마 확정 (13개 × 필드 + 링크 상태)]
    ├──requires──> [원본 PDF 텍스트 정리 + 링크 생존 확인 + 사용자 확인]
    ├──enables──> [프로젝트 카드 UI]
    │                 ├──requires──> [사용자 제공 스크린샷 (+ 최적화 변환)]
    │                 │                  └──requires──> [대체 텍스트 작성]
    │                 ├──enhances──> [라이트박스/갤러리]  (포커스 관리 필수)
    │                 └──enhances──> [플랫폼/회사 필터]  (v1.x)
    └──enables──> [Career 타임라인 → 프로젝트 앵커 링크]

[디자인 토큰 (타이포, 여백, 포인트 컬러)]
    ├──requires──> [명도 대비 검증]
    └──enables──> [모든 섹션 UI] ──enables──> [print stylesheet / PDF]

[시맨틱 마크업 + 반응형 + 접근성] (전 단계에 걸친 품질 기준)
    └──enables──> [Lighthouse/Validator 측정] ──enables──> [Colophon 섹션에 결과 표기]

[GitHub 공개 저장소]
    ├──requires──> [개인정보 파일 gitignore 검증 (전화번호, 제출용 PDF, .planning/source)]
    └──enables──> [Colophon의 소스 링크]

[웹 공개용 PDF (전화번호 없음)] ──conflicts──> [제출용 PDF (전화번호 있음)를 공개 경로에 두는 것]

[과한 애니메이션] ──conflicts──> [접근성 / 성능 점수 / 미니멀 방향]
```

### Dependency Notes

- **카드 UI는 데이터 스키마를 확정해야 만들 수 있다.** 13개 프로젝트의 필드(특히 링크 상태와 기여도 맥락)를 먼저 표 한 장으로 정리해 사용자 확인을 받아야 한다. 그러지 않으면 UI를 만든 뒤 콘텐츠가 맞지 않아 다시 고치게 된다. 콘텐츠 정리 단계를 가장 앞에 둔다.
- **스크린샷은 외부 의존이다.** 사용자가 이미지를 주기 전에는 카드 레이아웃을 플레이스홀더(실제 비율과 같은 크기)로 만든다. 앱 캡처(세로)와 웹 캡처(가로)의 비율이 섞이므로 카드 레이아웃은 두 비율을 모두 받을 수 있게 설계한다.
- **Colophon의 수치는 마지막에 확정된다.** 측정값은 사이트가 완성된 뒤에야 나온다. 섹션 틀은 먼저 만들고 값은 마지막 단계에서 채운다.
- **print stylesheet는 디자인 토큰과 섹션 마크업이 안정된 뒤에 만든다.** 마크업이 바뀌면 페이지 나눔이 다시 깨진다.
- **공개 저장소와 개인정보는 충돌할 수 있다.** 첫 커밋 전에 `.gitignore`를 검증해야 한다(PROJECT.md 기준으로 `.planning/source/`는 이미 제외되어 있다). 제출용 PDF 출력물도 제외 대상이다.

## MVP Definition

### Launch With (v1)

- [ ] 13개 프로젝트 데이터 시트(스키마 C) — 모든 화면의 기반이고, 사실관계를 확인하는 단계
- [ ] Hero, Skills(주력/경험), Career 타임라인, 프로젝트 카드 13개, Contact(이메일) — 원본 PDF 내용을 빠짐없이 옮긴다
- [ ] 일관된 링크/운영 상태 배지 — 운영 종료나 기사만 남은 작업이 많은 이 경력에서 신뢰도의 핵심
- [ ] 스크린샷 + 대체 텍스트 + 이미지 최적화
- [ ] 반응형 375/768/1440, 시맨틱, 키보드, 대비 AA, 크로스브라우징 — 사이트 자체가 증거
- [ ] OG/meta/favicon
- [ ] 같은 디자인의 PDF(웹 공개용은 전화번호 없음, 제출용은 전화번호 있음) + 다운로드 버튼
- [ ] Colophon(만든 방식 + 실측 검증 결과) + GitHub 소스 링크 — 비용이 낮고 차별 효과가 가장 크다

### Add After Validation (v1.x)

- [ ] 플랫폼/회사 필터 — 검토자 피드백에서 "찾기 어렵다"는 말이 나오면 추가
- [ ] 데스크톱+모바일 쌍 스크린샷 구성 확대 — 사용자가 캡처를 더 확보하면
- [ ] 다크모드 — 핵심 완성 후 대비 검증을 다시 할 여유가 있을 때
- [ ] 프로젝트별 "퍼블리싱 포인트" 보강 — 사용자가 근거 있는 내용을 추가로 줄 때

### Future Consideration (v2+)

- [ ] 영문 버전 — 해외나 외국계 지원 시(현재 Out of Scope)
- [ ] 개인 사이드 프로젝트 / 코드 샘플 섹션 — 공개할 수 있는 코드가 생기면
